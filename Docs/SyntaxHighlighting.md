# Adding syntax formats

Syntax highlighting has three layers:

- `SyntaxEngine` chooses a format from its registry, using a bounded sample of the note, then tokenizes the whole note. It discards cancelled results.
- Each `SyntaxDefinition` supplies content detection and UTF-16 token spans. YAML, JSON, Markdown, HTML, XML, CSS, Bash and the combined JavaScript/TypeScript/JSX mode live in separate `Syntax*.swift` files. These modules depend only on Foundation.
- `EditorSyntaxHighlighter` schedules background work and maps semantic token kinds to temporary foreground colors. It owns AppKit integration, brightness, and stale-result protection. It never changes text storage or undo history. It colors only the visible text plus one screen above and below, repainting as the view scrolls, resizes or switches tabs, and shares one color object per token kind. `SyntaxSpanIndex` (built on the background queue) finds the spans for that window by binary search and preserves the override order of overlapping spans.

To add a format:

1. Add a case to `NoteLanguage` in `SyntaxEngine.swift`.
2. Add `Sources/SyntaxYourFormat.swift` conforming to `SyntaxDefinition`, with `language`, `confidence(in:)`, and `highlight(_:)`.
3. Register its type in `SyntaxEngine.definitions`. No dispatch branches or editor changes are needed. Build and test scripts discover `Syntax*.swift` files automatically.
4. Add fixtures to `Tests/main.swift` covering positive detection, ambiguous prose, conflicts with existing formats, Unicode/CRLF offsets, unfinished edits and cancellation. For new editor behavior, extend the isolated native smoke tests.

Use `SyntaxSource.lines` for logical lines and their absolute UTF-16 offsets. Its `first`/`matches` methods share cancellable regex enumeration. Stateful syntaxes can use a lexer instead, as JavaScript does. Return `SyntaxSpan` values with existing semantic kinds whenever possible; the editor decides their colors. Ranges must be nonempty and within the complete source. Later overlapping spans override earlier ones, which allows Markdown's front matter to reuse YAML tokens. Single-pass lexers should emit non-overlapping tokens in source order.

Confidence values are comparable across formats: zero means no evidence; 1–69 is ambiguous; 70–94 is distinctive syntax; 95 and above identifies an enclosing format. Highest confidence wins. Equal scores retain registry order. Fenced Markdown and front matter should outrank enclosed snippets, and YAML block scalars should outrank code within them. Check strings and comments before treating their contents as language evidence. New formats should add evidence rather than raise scores to beat existing formats blindly.

Detection samples the first 32,768 characters, remains content based, and falls back to plain text when there is no evidence. JavaScript and TypeScript intentionally share the `javascript` language identifier and one lexer; TypeScript keywords and type names extend JavaScript's tokens. JSX elements are lexed speculatively wherever an expression may start; malformed markup, or an outer element with no closing tag anywhere later, rolls back so TypeScript generics and assertions lex as code. Components, fragments, `{…}` attributes and `className` are JSX evidence and outrank plain HTML. HTML reuses the JavaScript and CSS modules for `<script>` and `<style>` bodies by shifting their spans; a full document or one with script/style blocks is an enclosing format. Add a case to `NoteLanguage` in menu order; its raw value is stored in note metadata, so never rename one. Regex-versus-division detection is heuristic, and the lexer does not validate code or provide semantic type analysis. Markdown code fences retain a single code color. XML reuses the HTML scanner in XML mode (CDATA, declaration attributes, internal subsets, no embedded code); a note whose root is an HTML element stays HTML, and markup without JSX fragments, `{…}` attributes or `className` outranks JSX. The Bash lexer tracks command position, so keywords and commands are only recognized where the shell would read them; shell-only syntax (closed `then…fi`/`do…done`/`case…esac` blocks, `[[`, `[ -f`, `2>&1`, `/dev/null`, `set -e`, `local`, closed heredocs) outranks JavaScript, while two or more `word:` lines leave a note to YAML.

JSON uses its own UTF-16 lexer and an iterative prefix grammar to recognize objects and arrays without mistaking JavaScript expressions, unquoted YAML keys or quoted code for JSON. Incomplete strings, numbers and literals remain highlightable. Quoted keys use the shared key color, values use string/number/literal colors and delimiters use marker colors. Scalar-only JSON requires the manual override to avoid detecting ordinary prose as JSON. It is a tolerant highlighter, not a validator; JSONC/JSON5 and newline-delimited JSON have no separate modes. The `json` metadata value, Syntax menu item and Save As extension follow the same registry contract as other formats.

Run `./test.sh`, then `./build.sh`. Native smoke tests must use a fresh disposable `--data-dir` as documented in the README. Never use real notes for tests.
